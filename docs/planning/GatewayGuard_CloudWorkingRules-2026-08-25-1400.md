# Cloud working rules — how not to build on the wrong file

- **Document Name:** GatewayGuard_CloudWorkingRules
- **Last Modified:** 2026-08-25 14:00 ET
- **For:** Claude Cloud, every session, before any deliverable
- **Written because:** licence v2.2 was reconstructed from a readable twin
  because the `.docx` master could not be opened, and it carried forward a
  sentence from a superseded draft that attributed to the attorney something
  he never said. Neither failure was carelessness. **Both were the predictable
  result of working from what was reachable instead of from what was current.**

---

## THE PASTE-IN BLOCK

**Bill: paste this into Cloud at the start of any session where Cloud will
write a document.** Everything after it is the reasoning, which Cloud can read
in this file.

```
Before you write anything, do these five things and show me the answers.

1. Open ProjectDocs/CURRENT.md. Read out the four freshness values:
   Generated, Commit at generation, That commit was made, Its subject line.

2. Name the exact file you are going to build on, and find its row in
   CURRENT.md. If your base is not the file CURRENT.md names for that row,
   stop and tell me why.

3. Tell me how you read it. "Read in full", "read the .md twin because the
   .docx is not indexed", or "could not read it". If it is the third one,
   stop. Do not reconstruct a document you cannot read.

4. List every sentence you are carrying forward from an older draft that
   makes a factual claim -- who said something, what a machine does, what a
   number is. For each one, name the primary source you checked it against.
   A previous draft is not a source.

5. Tell me what you could NOT see, and what that might change.

Then write. Hold every question until the work is done, then put them all
at the end in one numbered list.
```

---

## RULE 1 — START FROM `CURRENT.md`, NEVER FROM A FILENAME THAT LOOKS RIGHT

`ProjectDocs/CURRENT.md` is generated by `Tool2/Update-Current.ps1` and names
the live file for every document family. **It is the only authority on which
file is current.** A filename that merely looks newest is not.

**Why this is not obvious.** `ProjectDocs/` holds four licence drafts, three
of them superseded and two of them formally withdrawn. Two carry dates within
a day of each other. **Nothing in the folder marks a file as dead.** A
reasonable reader picks the one with the latest-looking name and is wrong.

**The check is one line:** find your base file's row in `CURRENT.md`. If it is
not there, you are working on something nobody has declared current.

---

## RULE 2 — READ THE FRESHNESS STAMP OUT LOUD, EVERY SESSION

The top of `CURRENT.md` carries four values: **Generated**, **Commit at
generation**, **That commit was made**, and **Its subject line**.

**State all four in your first reply.** Bill compares them against what Claude
Code last pushed. A mismatch is one line instead of five searches.

**This exists because there is no other way to tell.** Anthropic support
confirmed on 2026-08-12 that the GitHub connector syncs into project knowledge,
exposes no live repository tool, and offers **no way to see which commit a
snapshot reflects.** So the stamp travels inside the payload — reading the file
*is* reading the sync date.

**If the newest file you can see is older than what `CURRENT.md` names, your
snapshot is stale. Say so and stop.** Do not work around it.

---

## RULE 3 — WHAT YOU CANNOT READ, YOU DO NOT REBUILD

**Measured: the connector does not index `.docx`, `.pdf`, `.pptx`, or images.**
Every binary in the repository has a generated `.md` twin beside it for exactly
this reason.

**The twin is for reading. It is not a base for authoring a replacement
master.** A twin is a projection: it loses tracked changes, comments, shading,
and any formatting that carries meaning. Rebuild a master from a twin and every
one of those is silently gone.

**So:** if the file you need is a binary, read its twin, work out **what should
change**, and hand Claude Code a numbered change list against the named master.
**Do not produce a replacement `.docx`.** Claude Code can open the master and
apply changes with assertions; you cannot.

**This is what happened with v2.2, and Cloud flagged it honestly** — the
provenance caveat in that handoff was the right instinct. **This rule turns the
caveat into a stop.**

---

## RULE 4 — A PREVIOUS DRAFT IS NOT A SOURCE

**The rule that would have caught the real error.** The sentence *"withdrawn on
the attorney's advice and Bill's judgment"* first appeared in the 2026-08-07
draft. It was true of nothing. It was then carried into the 2026-08-24 draft
by Claude Code and read past twice.

**A sentence in a draft looks sourced because it is written in the same
confident register as the sentences that are.** Nothing about it says
*"nobody checked this."*

**So, before carrying any factual claim forward from an older document, name
the primary source:**

| Kind of claim | The primary source |
|---|---|
| What Bill said | `GatewayGuard_AttorneyConsultNotes-Bill-VERBATIM-*.md` — his own words |
| What the attorney said | the same file, the attorney's recorded answers |
| What the software does | the build `.ps1` in `Tool/`, by function and line |
| What a machine's state is | a file in `Test_Results/` |
| A price or a policy | the decision document named in `CURRENT.md` |
| A date or a commit | `CURRENT.md`'s freshness stamp |

**If you cannot name one, write "not verified" and move on.** That is always
acceptable. A wrong claim in a contract is not.

---

## RULE 5 — EVERY STATE CLAIM CARRIES ITS SOURCE IN THE SENTENCE

This is `CLAUDE.md`'s standing rule and it applies to Cloud identically. Any
sentence asserting the state of a machine, a file, or a behaviour carries, **in
that sentence**, the thing it was read from — a path and line, a command and
its output, or a file in the repository.

**Use the four labels: measured, sourced, inferred, guess.** A claim with no
label is being asserted as fact, so it had better be one. **`inferred` and
`guess` are never shippable into a customer-facing document.**

**Bill's four-word check on any claim: "What did you read?"** If the answer is
not a path, a command, or a quote, the claim is not ready.

---

## RULE 6 — ANNOUNCE PROVENANCE AT THE TOP OF EVERY DELIVERABLE

Four lines, before the content:

```
Base file      : <exact filename, matching its CURRENT.md row>
How I read it  : in full / .md twin only / could not read
Could not see  : <what was unreadable, and what it might change>
Sync stamp     : <the four CURRENT.md freshness values>
```

**This is cheap and it is the whole defence.** The v2.2 handoff had a version
of it, voluntarily, and that is the only reason the reconstruction was caught
before it became the master.

---

## RULE 7 — DATES IN FILENAMES ARE THE ORDERING, AND THEY INCLUDE THE TIME

The convention is `filename-YYYY-MM-DD-HHMM.ext`, US Eastern. **`Update-Current.ps1`
resolves "newest" from the date in the filename, so two same-day files with no
time are a tie, and a tie resolves silently and arbitrarily.**

**That is not hypothetical:** on 2026-08-22 the pricing row resolved to a
superseded draft because the sort could not separate two same-day files, and
nothing said so.

**Fixed-name pointers carry no date at all** — `CURRENT.md`, `CLAUDE.md`,
`Start-Claude-Cloud.txt`. Their value is that the name never goes stale. **Never
add a date to one of these.**

---

## RULE 8 — HOLD ALL QUESTIONS TO THE END

Bill's standing instruction. Do the research, do the analysis, reach a
recommendation on each item, **then** put every question in one numbered list at
the end. **Do not stop mid-way to ask.**

**And apply the test before asking at all:** imagine both answers. If you would
do the same thing either way, it was never a question. Act, and report what you
did and how to undo it.

**Ask only these four:** two real paths with different consequences where the
choice is Bill's; deleting something unrecoverable; anything that changes what
other copies believe; something outside the task you were given.

---

## RULE 9 — WHEN TEN MINUTES OF DIAGNOSIS HAS NOT FOUND A CAUSE, WRITE IT UP

**Not a theory. A cause.** The tell is repeated re-diagnosis: a second theory is
normal, a third means the answer is somewhere you cannot reach.

On 2026-08-12 the question *"why can't Cloud see the current files?"* consumed
most of a day and produced four wrong diagnoses in sequence. **One support
exchange settled it in a single reply**, and nothing in the repository could
have revealed the answer.

**Write up: environment, what was expected, what happened, every check with its
actual output, the numbered questions, and what the fault costs this project.
Then hand it to Bill and stop theorising.**

---

## THE ONE-LINE VERSION

**Name your base from `CURRENT.md`, say how you read it, and never carry a
factual sentence forward without naming what you checked it against.**

Those three cover both of the failures this document exists to prevent.
