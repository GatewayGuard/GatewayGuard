---------------------------------------------------------------
 STEP 1 -- SET UP THE FOLDER BEFORE YOU TYPE claude
---------------------------------------------------------------

Open PowerShell (or Windows Terminal) and paste this line:

cd "C:\Users\willi\OneDrive - GatewayGuard LLC\GatewayGuard"

Then, and only then, type:

claude

THE QUOTES ARE REQUIRED. The path contains a space, at
"OneDrive - GatewayGuard LLC". Without quotes PowerShell reads
it as three arguments and you land somewhere else.

THE PATH ENDS IN \GatewayGuard. Stopping one folder short, at
"...\OneDrive - GatewayGuard LLC", is the easy mistake and it
is a quiet one -- the folder exists, the cd succeeds, and
Claude Code starts normally. What it does NOT do is load
.claude\settings.local.json, because that now sits in a
SUBFOLDER rather than the session root. The .ps1 integrity
hook does not arm. The permission allowlist does not apply.
The website-copy rule does not trigger. Bare git finds no
repository at all, because git searches upward, never down.

Nothing announces any of this. Happened 2026-08-10, on the
first use of this file.

DO NOT start it in Attachments\GatewayGuide\ either -- that is
a stale copy of the whole tree, with its own .git, nested
inside the working tree. It looks right and is not.

TO CHECK, once claude is running, ask it to print its working
root. That is step 2 of the paste block below, and this is the
failure it exists to catch.

---------------------------------------------------------------
 WHY EACH STEP IS THERE
---------------------------------------------------------------

1. GET-DATE. Claude Code can read the clock. Cloud has to ask
   and Claude Code copied the habit. Every file here is named
   and stamped with a date, so a wrong date is a wrong filename.

2. CONFIRM THE ROOT. Six copies of this tree have existed at
   three different commits. One is still nested inside the
   working tree at Attachments\GatewayGuide\, complete with its
   own .git. Printing the path costs one line and catches the
   one failure that makes an entire session's work land in the
   wrong folder.

3. GIT STATUS. On 2026-08-08 a stray drag in File Explorer
   moved ProjectDocs\ -- every governing document -- inside
   Recovery Keys\, and moved WebSite\ inside Tool\. Windows does
   that on a same-drive drag with no confirmation and no undo
   prompt. It went unnoticed for over an hour. git status
   reported it instantly. The tree carries deliberate deletions
   and untracked holdbacks, so "not clean" is the correct state
   -- what matters is whether the numbers moved since last time.

4. NEWEST BY FILENAME DATE. Three copies of the Playbook exist.
   Sorting by modified date returns one 13 days stale. Trusting
   a filename written out inside a briefing returns one a day
   stale. Only the date in the filename returns the current one.
   Known exception: LegalZoomGuide-2026-07-24-0846 is newer than
   -0921.

   THE SESSION LOG AND PROJECT INSTRUCTIONS ARE NEW HERE. Both
   carry a standing "read at every session start" rule, and the
   briefing alone does not replace them. The SessionLog only
   reached the tree on 2026-08-09 -- before that Claude Code had
   never read it, because it could not.

5. THE STALE CHECK IS THE POINT. Every briefing so far has gone
   stale within hours, including two pointers in one written the
   same afternoon. Asking for it up front turns a silent trap
   into the first thing you are told.

   ASKING FOR THE BUILD'S FIELD LOG, not just the build number,
   is what enforces the UNRUN BUILD RULE: nothing may be scoped
   or numbered as the next build until the current one has been
   field run.

   AND IT MUST LOOK ON DISK. On 2026-08-12 this step answered
   "no field log exists for ascii39" while
   Test_Results\Ascii39-Test-Results-2026-08-11-2237.txt sat in
   the folder. It was untracked, so git could not see it, and
   the check had only asked git. A question answered with a tool
   that is blind to the answer returns a confident wrong number.
